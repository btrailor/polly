# Polly Security Guide

**Last Updated:** February 3, 2026  
**Phase:** 23.5 (Security Hardening)

## Overview

Polly implements comprehensive security measures to protect your data and system while maintaining a smooth user experience. This guide explains how security features work and how to configure them.

**Key Security Principles:**
- **Capability Broker Pattern** - LLM requests capabilities, doesn't have direct access
- **Sandboxed Code Execution** - All code runs in isolated Pyodide environment
- **Package Allowlist** - Pre-approved packages + approval workflow
- **Content Sanitization** - Detect and warn on suspicious content
- **PII Detection** - Warn before sending sensitive data to cloud APIs
- **Secure API Key Handling** - Keys cleared from memory after use

## Code Execution Security

### Pyodide Sandbox

All Python code execution happens in a **Pyodide sandbox** (Python compiled to WebAssembly). This provides:

- ✅ **No network access** - Code cannot make network requests
- ✅ **No filesystem access** - Code cannot read/write files
- ✅ **Timeout protection** - Code execution limited to 10 seconds (configurable)
- ✅ **Memory limits** - Code limited to 512MB memory (configurable)
- ✅ **Isolated execution** - Code runs in browser security model

**Where it's used:**
- Curriculum exercise execution
- Code examples in learning materials
- Any Python code generated by Polly

**Configuration:** `config/security_policy.yaml`
```yaml
sandbox:
  type: pyodide
  timeout_seconds: 10
  memory_limit_mb: 512
  network_access: false
  filesystem_access: false
```

## Package Management Security

### Package Allowlist

Polly uses a **package allowlist** to control which Python packages can be used in generated code.

**How it works:**
1. **Python Standard Library** - Always allowed (no approval needed)
2. **Pre-approved Packages** - ~100 common, safe packages (numpy, pandas, requests, etc.)
3. **Unknown Packages** - Require user approval before use

**Approval Workflow:**
1. Polly generates code with a package (e.g., `import new_package`)
2. Package Detector scans the code
3. If package is not in allowlist, execution is **blocked**
4. Approval dialog appears showing:
   - Package name and description (from PyPI)
   - Context7 trust score (if available)
   - Usage statistics
5. You can: **Approve**, **Deny**, or **Permanently Block**

**Context7 Integration:**
- Polly leverages Context7's library trust scores
- Packages with trust score >= 7 can be auto-approved (configurable)
- Trust scores help you make informed decisions

**Configuration:** `config/approved_packages.yaml`
```yaml
approved_packages:
  - numpy
  - pandas
  - requests
  # ... ~100 pre-approved packages

context7:
  use_trust_score: true
  min_trust_score: 7  # Auto-approve if >= 7
```

**Managing Approved Packages:**
- Add packages to `config/approved_packages.yaml`
- Or approve packages via the approval dialog
- Approved packages are cached to your user config

## Capability Broker

The **Capability Broker** is the central security boundary for all high-risk operations.

**How it works:**
- LLM requests capabilities (e.g., "install package X")
- Broker validates the request
- Checks security policy
- Requires approval if needed
- Logs all requests to audit database

**Capability Types:**
- **PACKAGE_INSTALL** - Package installation requests (always require approval)
- **SHELL_EXEC** - Shell command execution (disabled by default)
- **API_CALL** - API calls (for rate limiting, not blocking)

**Audit Logging:**
- All capability requests logged to `~/.polly/audit.db`
- Retention: 90 days (configurable)
- Logs include: timestamp, capability type, requestor, resource, status

**Configuration:** `config/security_policy.yaml`
```yaml
capabilities:
  package_install:
    enabled: true
    require_approval: true
    show_context7_info: true
```

## Content Security

### Prompt Injection Detection

Polly detects **prompt injection patterns** in documents that might hijack LLM behavior.

**Patterns Detected:**
- "Ignore previous instructions"
- Role-playing patterns ("You are now...")
- Base64/Unicode obfuscation
- System/User role markers

**How it works:**
- Content is scanned before being sent to LLM
- Suspicious patterns are detected
- **Warning shown** (not blocking - you decide)
- You can choose to send the content anyway

**Configuration:** `config/security_policy.yaml`
```yaml
content_security:
  scan_for_prompt_injection: true
  prompt_injection_sensitivity: medium  # low | medium | high
  warn_on_suspicious_content: true
  block_suspicious_content: false  # Warning only
```

### PII Detection

Polly detects **Personally Identifiable Information (PII)** in content before sending to cloud APIs.

**PII Types Detected:**
- Email addresses
- Phone numbers
- Social Security Numbers (SSN)
- Credit card numbers
- API keys (in content)

**How it works:**
- Content is scanned before cloud API calls
- PII patterns are detected
- **Warning shown** (not blocking - you decide)
- You can choose to send the content anyway

**Configuration:** `config/security_policy.yaml`
```yaml
pii_detection:
  enabled: true
  warn_only: true  # Warn but don't block
  user_can_disable: true  # You can disable warnings
```

## API Key Security

### Secure Key Handling

Polly uses **context managers** to ensure API keys are securely handled.

**How it works:**
- Keys are loaded only when needed
- Keys are cleared from memory immediately after use
- Keys never linger in memory
- Secure cleanup pattern enforced

**Key Rotation:**
- Polly reminds you to rotate keys every 90 days (configurable)
- Rotation helpers available in settings
- Old keys are securely removed

**Configuration:** `config/security_policy.yaml`
```yaml
api_keys:
  use_secure_context_manager: true
  auto_cleanup_memory: true
  rotation_reminder_days: 90
```

## CORS Policy

Polly's CORS policy is restricted to prevent unauthorized access.

**Allowed Origins:**
- `http://localhost:*` - Local development
- `http://127.0.0.1:*` - Localhost alternative
- `http://100.64.0.0/10` - Tailscale CGNAT range (for remote access)

**Configuration:** `config/security_policy.yaml`
```yaml
cors:
  allowed_origins:
    - http://localhost:*
    - http://127.0.0.1:*
    - http://100.64.0.0/10
  allow_credentials: true
```

## Configuration

### Security Policy

Main security configuration: `config/security_policy.yaml`

**Security Modes:**
- `personal` - Optimized for single-user (current default)
- `team` - More restrictive (future)
- `public` - Maximum security (future)

**Key Settings:**
- `security_mode` - Overall security level
- `capabilities.*` - Capability broker settings
- `sandbox.*` - Code execution sandbox settings
- `content_security.*` - Content sanitization settings
- `api_keys.*` - API key security settings
- `audit.*` - Audit logging settings
- `cors.*` - CORS policy settings

### Package Allowlist

Package allowlist: `config/approved_packages.yaml`

**Sections:**
- `stdlib_modules` - Python standard library (always safe)
- `approved_packages` - Pre-approved packages (~100)
- `blocked_packages` - Explicitly blocked packages
- `context7.*` - Context7 integration settings

## Best Practices

### For Personal Use

1. **Review Package Approvals** - When Polly suggests a new package, review the Context7 trust score before approving
2. **Monitor Audit Logs** - Check `~/.polly/audit.db` periodically to see what capabilities were requested
3. **Rotate API Keys** - Follow rotation reminders to keep keys secure
4. **Review Warnings** - Pay attention to PII and prompt injection warnings

### For Team Use (Future)

1. **Stricter Policies** - Use `team` security mode when available
2. **Centralized Allowlist** - Maintain team-wide package allowlist
3. **Audit Reviews** - Regular reviews of audit logs
4. **Key Management** - Centralized API key management

## Troubleshooting

### Code Execution Fails

**Problem:** Code execution times out or fails  
**Solution:**
- Check timeout settings in `config/security_policy.yaml`
- Increase `timeout_seconds` if needed
- Check memory limits

### Package Approval Not Working

**Problem:** Approval dialog doesn't appear  
**Solution:**
- Check `config/security_policy.yaml` - ensure `package_install.enabled: true`
- Check `config/approved_packages.yaml` - ensure package is not already approved
- Check browser console for errors

### Too Many Warnings

**Problem:** Getting too many PII or prompt injection warnings  
**Solution:**
- Adjust sensitivity in `config/security_policy.yaml`
- Set `pii_detection.user_can_disable: true` to disable warnings
- Lower `prompt_injection_sensitivity` to `low`

### Context7 Trust Scores Not Showing

**Problem:** Context7 trust scores not appearing in approval dialog  
**Solution:**
- Check Context7 integration is connected (Settings → Integrations)
- Verify `context7.use_trust_score: true` in `config/approved_packages.yaml`
- Check Context7 API key is valid

## Security Architecture

**Request Flow:**
```
User/LLM Request
      ↓
Capability Broker
  - Validates request
  - Checks policy
  - Logs to audit.db
  - Requires approval if needed
      ↓
Approved Operation
  - Pyodide Sandbox (code execution)
  - Package Manager (with allowlist)
  - API Gateway (secure key handling)
```

**Security Layers:**
1. **Input Validation** - All API requests validated
2. **Capability Broker** - Centralized security boundary
3. **Sandbox** - Isolated code execution
4. **Content Sanitization** - Prompt injection detection
5. **PII Detection** - Privacy protection
6. **Audit Logging** - Complete audit trail
